Codebase audit

What exists in the repository today, audited on 6 September 2026.

Nothing is implemented. The repository is two plan documents, eight .skill archives, and two reference files. No bot/, no migrations, no tests, no docker-compose.yml, no CI workflows. Every artifact in the plan is net-new.

That is good news for one specific reason: the domain/-purity boundary that makes the replay harness possible can be established in week 1 rather than retrofitted in week 7, when it would cost more than the harness is worth.

What gets built — the 13-state incident lifecycle

  • detected
  • triaging
  • engaged
  • acknowledged
  • mitigating
  • mitigated
  • resolved
  • reopened
  • pir_drafting
  • pir_drafted
  • pir_failed
  • closed
  • merged
  • false_positive
  • abandoned

Bordered states are terminal. The transition table exists twice — as a Python dict that catches programmer error at development time, and as UNIQUE (incident_id, seq) that catches concurrency error at 3 a.m.

Source hierarchy

Applied consistently throughout the plan. Where two sources disagree, the higher tier wins and the resolution is recorded.

  1. Implementation Plan Rev 2 — primary. Architecture, defect fixes, version pins, differentiators.
  2. The eight project skills — binding as project rules. Their “Critical rules” become invariants; their “Definition of done” become acceptance criteria.
  3. Starter code reference — the reference implementation. Where it and Rev 2 show the same function differently, it wins; every case is logged.
  4. Schema and eval-harness references — authoritative for the data layer and the eval harness, superseding the abbreviated versions in Rev 2.
  5. Rev 1 — last resort, only for content Rev 2 references but never enumerates. Used exactly once, for the runbook catalogue, and labelled as such.

The findings that matter

Reading Rev 2, the starter code and the two reference files against each other surfaced eleven disagreements and four places where a source is wrong on its own terms. These seven are the ones that would have cost real time or shipped a silent bug.

C-05Critical · silent failure

The skeleton PIR is generated, persisted — and never posted

Rev 2’s EFFECTS table omits (PIR_FAILED → PIR_DRAFTED), which the starter code maps to post_pir_skeleton. Without it that transition fires no outbox event, so the incident reaches pir_drafted with nothing visible in the channel.

This is the highest-consequence conflict in the set because it breaks the week 6 acceptance gate — “skeleton posted within 90 s” — while every unit test still passes.

ResolutionUse the starter code’s EFFECTS table verbatim, including post_merge_notice on the merge edge.
X-01Critical · does not run

The dead-step analytics query is not valid SQL

Q5 in the schema reference has three independent errors: unnest() appears both in the select list and as a CROSS JOIN LATERAL, producing a cross product; the FILTER clause references a different expansion than the one it groups by; and the outer query aliases runbooks as r while the subquery already exposes r.name.

It is the input to differentiator D4’s runbook-efficacy loop, so shipping it means that loop silently produces nothing.

ResolutionCorrected query committed in the plan as task W5-14, with test_dead_step_query_runs executing it against a seeded Testcontainer.
C-03High · non-determinism

First-match correlation makes storm outcomes depend on sort order

Rev 2’s correlate() returns on the first incident clearing the 0.62 threshold; the starter code returns the best-scoring match. During a storm several open incidents clear the bar at once, so first-match ties the merge target to the database sort order of open_incidents.

That is exactly the run-to-run variance the replay harness exists to exclude. Rev 2’s version also drops the severity guard its own prose promises — a Sev1 could be absorbed into a Sev3.

ResolutionBest-match wins, severity guard retained, cfg passed as a parameter rather than imported — which is also what makes the eval harness’s counterfactual mode possible.
X-03High · missing implementation

dedup_epoch is central to idempotency and nothing writes it

Rev 2 and the ingest skill both explain that the epoch increments when an incident closes so the same alert can recur next week, and UNIQUE (dedup_key, dedup_epoch) depends on it. No source contains the code that increments it, or says where the next epoch is read from.

ResolutionDerive it, never store it globally: try the open-incident lookup first, then insert with COALESCE((SELECT max(dedup_epoch)+1 …), 0) inside the transaction already holding the advisory lock. If two workers still race, the unique constraint remains the arbiter.
C-02High · breaks the demo

The compose file aborts on the very clone it promises will work

Rev 2 §13.2 sets IP_SLACK_SIGNING_SECRET: ${SLACK_SIGNING_SECRET:?set in .env}. The :? operator makes Compose abort when the variable is unset — while the paragraph directly below promises an interviewer can clone and run the full demo without credentials.

A fake LLM provider alone is also not enough: channel creation still calls a Slack API that will reject the token. Rev 2 never mentions the chat provider.

ResolutionDefault the Slack variables with :- and add IP_CHAT_PROVIDER=fake, so a clean clone with no .env runs the storm, the war room and the PIR end to end.
X-04High · arithmetic

The TimescaleDB justification assumes a resolution Prometheus does not produce

Rev 2 justifies the hypertable on “20 series × 1-second resolution × 60 minutes = 72,000 rows per incident.” Prometheus scrapes at 15 s by default, so one-second resolution does not exist in the source data — a step=1s range query returns an interpolated staircase. The real figure is roughly 4,800 rows per incident.

This is the second correction to the same number; Rev 2 already corrected it once.

ResolutionKeep the conclusion, fix the reasoning. What survives is declarative retention and compression replacing ~150 lines of cron and partition maintenance, plus time_bucket_gapfill() for the incident chart. The decision doc records both corrections — consistent with Rev 2’s own principle that a decision document hiding its revisions is worthless.
X-02Medium · lost evidence

The alerts table cannot record that an alert re-fired

UNIQUE (fingerprint, starts_at) is the correct idempotency guard, but Alertmanager re-sends a firing alert every repeat_interval with the same startsAt — that field is when the alert began, not when it was sent. So the retry is a silent no-op and received_at holds the first receipt forever.

ResolutionKeep the constraint; add last_seen_at and seen_count updated via ON CONFLICT … DO UPDATE. Two columns turn a silent no-op into evidence, and “Alertmanager re-sent this four times before we mitigated” is a real PIR sentence.

Eight weeks, eight binary gates

A red gate stops the week. That is the point of having them — and “I cut scope when week 6’s gate went red” is a better answer than a plan that never slipped.

  • domain/ purity test, before the code it guards
  • The 15 Prometheus metrics; SLOs written first
Gate G1Bad bearer → 401; good → 202 at p99 < 250 ms over 100 requests; entry visible on the stream
2Correlation & state machine

Forty alerts become one incident. Thirteen states, enforced twice. 15 tasks.

  • Full schema; alembic upgrade head from empty
  • Best-match correlation with the severity guard
  • Root signal = first alert on the deepest dependency

The best demo of idempotency in the project. 16 tasks.

  • Transactional outbox; the relay is the only external writer
  • Twelve crash points, injected and tested
  • Priority lanes — shed the decorative, never the critical
Gate G3Kill the worker mid-orchestration, restart → no duplicate channel, 12/12 crash points
4Event-sourced transcript

Slack becomes a write path, not a read path. 13 tasks.

  • Every message persisted as it arrives
  • Edits appended as revisions, never applied in place
  • The reconciler is the sole history caller, 1/min
Gate G4200 messages → 200 rows, zero duplicates, zero history calls
5Responders & runbooks

The right human, aware of how much they have already been paged. 17 tasks.

  • Fatigue scoring; never a silent reroute
  • Eight runbooks with parseable step IDs
  • Runbook matched to the root signal, not the loudest alert
Gate G5Pager unreachable → cache → static rota → team channel, each announced. Silent failure fails the gate
6Impact & the grounded PIR

The flagship. Impact is computed before any model call. 23 tasks.

  • Six citation kinds with a stable ID grammar
  • Deterministic validator — no model in the gate
  • Root cause nullable; “unknown” is a valid answer
Gate G6Provider blocked → skeleton in 90 s. Unblocked → full PIR, zero uncited claims
7Replay harness & eval gate

The crown jewel — nothing in the OSS incident field has this. 22 tasks.

  • 40 incidents, 11 buckets, adversarial fixtures included
  • Hard gates deterministic; judge agreement reported
  • Lifeboat: separate image, no shared dependencies
Gate G7A one-word prompt change turns CI red and blocks the PR. Screenshot it
8Dashboard, deploy, polish

Runs for a stranger, from a clean clone, with no API key. 18 tasks.

  • Server Components by default; citation chips resolve
  • Helm chart with no secrets.yaml, ever
  • Signed images, atomic deploy, smoke test, rollback

Open decisions

Four calls the plan could not make on your behalf. Three have a default applied so nothing is blocked; one needs an answer before week 6.

E-1Needs an answer · before week 6

The synthesize model default

Rev 2 flags that a current-generation small model now sits roughly 4× below the committed default, and deliberately did not change your portfolio baseline. The plan follows that — GPT-5.4-mini ships as the default for consistency with your other capstones.

The mechanism to settle it is built in week 7, and this is the best possible use of it: replay the corpus with --set roles.synthesize.model=<candidate>, compare quality and cost against the committed baseline, and promote whichever wins on your own golden set. That turns a price-list argument into an evidence-backed decision — which is the interview story.

E-2Default applied

Prometheus scrape interval for the demo cluster

15 s scrape with a matching sampler step, and the corrected arithmetic recorded honestly. A 5 s interval would restore the larger row count at the cost of a non-default config you would have to explain. Recommendation: keep 15 s and keep the correction — a second self-caught arithmetic error is a better answer to “what did you get wrong” than a bigger number.

E-3Default applied

D4’s auto-PR job — ship or defer?

Deferred to post-MVP. The query filters on five uses per runbook, and you will not have five incidents per runbook inside eight weeks, so the job would run and produce nothing. Build the signal capture and the corrected query in week 5 — that is what the interview answer actually describes — and say the loop has not closed yet. Claiming a closed loop that has never closed is exactly what a follow-up question exposes.

E-4Default applied

Portfolio-wide version sweep

This plan pins slack-bolt 1.30.0 and Alertmanager 0.34.0, both newer than the HealOps and ChaosProof pins. If you bump Alertmanager in one project, bump it in all three — 0.34.0 splits two values out of the reason label, and any dashboard panel matching the old value will silently under-count.
